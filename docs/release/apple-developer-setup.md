## Часть 0. Что вообще происходит и зачем эти экраны

У Apple четыре РАЗНЫЕ сущности, которые новички путают между собой. Они живут в двух разных
сайтах и делают разные вещи:

| Сущность | Где заводится | Что это | Видит ли пользователь |
|---|---|---|---|
| **App ID (Identifier)** | developer.apple.com | Техническая «прописка» приложения. Именно она разрешает приложению пользоваться iCloud, уведомлениями и т. д. | Нет |
| **App Group** | developer.apple.com | Общая папка для приложения и виджета. Без неё виджет не видит данные приложения | Нет |
| **iCloud Container** | developer.apple.com | Хранилище в iCloud, куда синхронизируются данные | Нет |
| **Запись приложения** | appstoreconnect.apple.com | Карточка в магазине: имя, иконка, описание, скриншоты, цена | Да |

Сейчас ты на первой строке. Это техника, не витрина. Ничего из того, что ты тут напишешь,
пользователь никогда не увидит.

**Nenita состоит из двух бандлов** (двух отдельных программ внутри одной):

1. само приложение — `com.nenita.app`
2. виджет для домашнего экрана — `com.nenita.app.widget`

Поэтому App ID нужно **два**. Виджет — это отдельный исполняемый файл, Apple требует для него
собственный идентификатор.

## Часть 1. Ответы на твои вопросы

### ❓ Что писать в Description?

Это просто человеческое название строки в списке идентификаторов — чтобы ты сам через год
понял, что это. На магазин, на приложение, на пользователя оно не влияет никак.

**Пиши: `Nenita`**

Ограничения: нельзя `@ & * "` и другие спецсимволы. Латиница, цифры, пробелы, дефис — можно.
Кириллицу лучше не использовать (Apple местами её переваривает плохо).

Для второго идентификатора напишешь `Nenita Widget`.

Кнопка **Continue** сейчас серая именно потому, что Description пустой — это единственное, чего
не хватает.

### ❓ Что будет, если поставить только те галочки? Остальное потом нельзя добавить?

**Можно добавить потом. В любой момент, включая после релиза в App Store.**

Как это делается позже: developer.apple.com → Certificates, Identifiers & Profiles →
Identifiers → кликнуть на нужную строку → поставить/снять галочки → Save. Всё, 15 секунд.

Три оговорки, чтобы ты знал заранее:

1. **Добавлять — безопасно, убирать — нет.** Если приложение уже вышло и ты выключишь iCloud
   или App Groups, у живых пользователей отвалится синхронизация и данные, которые лежали в
   общем хранилище. Поэтому «на всякий случай наставить всё подряд» — плохая идея не потому,
   что нельзя добавить, а потому что потом неудобно откатывать.
2. **После изменения галочек Apple аннулирует профили подписи.** Звучит страшно, но у нас
   `CODE_SIGN_STYLE: Automatic` — Xcode молча перевыпустит их при следующей сборке. Ты этого
   даже не заметишь.
3. **Часть возможностей требует заявки и одобрения Apple** (CarPlay, доступ к камере в
   многозадачности и т. п.) — они живут во вкладке *Capability Requests*, там ожидание может
   быть неделями. Нам ничего из этого не нужно.

Чего изменить **нельзя** — это сам bundle ID `com.nenita.app` после того, как к нему
привязана запись в App Store Connect. Вот это правда навсегда. См. Часть 6.

### ❓ Что значит «потом пойти в Xcode и что-то там сделать»?

Xcode — это программа, в которой из исходного кода собирается файл приложения и отправляется
в Apple. Она у тебя установлена (версия 26.3, я проверил).

Разделение труда такое:

**Только ты (нужен твой Apple ID и пароль, я туда не имею доступа):**
- один раз залогинить Apple ID в Xcode: Xcode → Settings (⌘,) → Accounts → «+» → Apple ID

**Всё остальное делаю я из терминала:**
- прописать Team ID в настройки проекта
- пересобрать файл проекта
- собрать архив приложения
- подписать его
- загрузить сборку в App Store Connect (API-ключ для этого у тебя уже настроен —
  `/Users/roman/lets-tour-aso/AuthKey_4HWP33LMWN.p8`)

То есть «пойти в Xcode» в старой инструкции = «сказать Клоду собрать и залить». Единственный
ручной шаг — логин в Accounts, потому что там двухфакторка на твой телефон.

## Часть 3. 🧑 Создать App Group и iCloud Container

Сами «коробки» ещё не существуют — их надо создать отдельно, теми же двумя кликами.

**App Group:**
1. Identifiers → синий «+» вверху
2. в списке типов выбрать **App Groups** → Continue
3. Description: `Nenita App Group`
4. Identifier: `group.com.nenita.app` — **строго так, буква в букву**
5. Continue → Register

**iCloud Container:**
1. Identifiers → «+» → **iCloud Containers** → Continue
2. Description: `Nenita iCloud`
3. Identifier: `iCloud.com.nenita.app` — **строго так**. Поле может само подставлять
   префикс `iCloud.`; тогда дописываешь только `com.nenita.app`
4. Continue → Register

> ⚠️ Эти две строки должны совпадать с тем, что записано в проекте (`project.yml`, блок
> `entitlements`), символ в символ. Опечатка = приложение собирается, но при запуске падает
> или молча не синхронизируется. Если решишь написать иначе — скажи мне, я поправлю код.

## Часть 9. 🧑 Экран «New App» в App Store Connect

Это уже **второй сайт** — appstoreconnect.apple.com, витрина. Здесь создаётся карточка
приложения в магазине. Идентификаторы с developer.apple.com сюда только подставляются из
выпадающего списка, заново ничего регистрировать не надо.

| Поле | Что ставить | Можно ли поменять потом |
|---|---|---|
| **Name** | `Nenita` | Да, пока версия не ушла на ревью |
| **Primary Language** | English (U.S.) | Да, в App Information |
| **Bundle ID** | `com.nenita.app` — **основное приложение, НЕ `.widget`** | Практически нет, см. ниже |
| **SKU** | `nenita-ios-001` | **Нет, никогда** |
| **User Access** | оставить Limited Access как есть | Да, в Users and Access |

### Bundle ID — какой из двух выбирать

В выпадающем списке будут оба зарегистрированных идентификатора: `com.nenita.app` и
`com.nenita.app.widget`. Выбирать **`com.nenita.app`**.

Виджет никогда не получает собственную карточку в App Store. Он едет внутрь приложения как
часть сборки — пользователь скачивает одно приложение, а виджет появляется в галерее виджетов
сам. Отдельный App ID виджету нужен был только для подписи кода, к магазину он отношения не
имеет.

Технически ASC разрешает поменять bundle ID, пока не залита первая сборка. Считай, что нельзя:
после первой загрузки — только новая карточка с нуля.

### SKU — что это такое

**S**tock **K**eeping **U**nit, «складской артикул» — термин из розничной торговли, Apple
притащила его в ASC. Это твой внутренний код приложения:

- **пользователи его не видят никогда** — ни в сторе, ни в чеке, нигде
- всплывает только в твоих финансовых отчётах и выгрузках продаж, чтобы различать приложения
- должен быть уникальным **внутри твоего аккаунта** (не во всём мире, в отличие от bundle ID)
- **не меняется после создания** — вообще, никак, даже поддержкой
- допустимы латиница, цифры, `-`, `_`, `.`; нельзя начинать с дефиса, точки или подчёркивания

Никакого технического значения не имеет. В твоём же аккаунте лежат приложения с SKU `12345`,
`ok12345` и `dsf8as76dfa` — и всё работает.

**Ставь `nenita-ios-001`.** Осмысленно, читается в отчётах, не конфликтует ни с чем.

### User Access

Кто из членов твоей команды в ASC видит это приложение. Сейчас выбран Limited Access и уже
подставлены роли Admin / Finance / Reports плюс ты — этого достаточно. Меняется в любой момент
через Users and Access. Full Access = видят все шесть человек; разницы для тебя нет.

После **Create** карточка создана, но пустая: дальше заполняются описание, скриншоты, категория,
цена, политика конфиденциальности и создаются подписки (`com.nenita.app.premium.monthly` и
`.yearly` — символ в символ, как в коде). Это уже отдельный большой разговор, см.
[app-store-connect-testflight.md](app-store-connect-testflight.md).

### Как выпускать следующие билды

**Каждая загрузка требует нового номера билда.** Версия может остаться `1.0.0`, а
`CURRENT_PROJECT_VERSION` в `project.yml` обязан вырасти: 1 → 2 → 3. Apple отклоняет повторный
номер.

```bash
# 1. поднять CURRENT_PROJECT_VERSION в project.yml, затем:
xcodegen generate

KEY="-authenticationKeyPath /Users/roman/lets-tour-aso/AuthKey_4HWP33LMWN.p8 \
     -authenticationKeyID 4HWP33LMWN \
     -authenticationKeyIssuerID 69a6de7e-941a-47e3-e053-5b8c7c11a4d1"

# 2. архив
xcodebuild archive -project BabyBloom.xcodeproj -scheme BabyBloom \
  -destination 'generic/platform=iOS' -configuration Release \
  -archivePath build/Nenita.xcarchive -allowProvisioningUpdates $KEY

# 3. экспорт + загрузка (ExportOptions.plist с <key>destination</key><string>upload</string>)
xcodebuild -exportArchive -archivePath build/Nenita.xcarchive \
  -exportOptionsPlist build/UploadOptions.plist -exportPath build/upload \
  -allowProvisioningUpdates $KEY
```

Билд сам попадёт в группу Internal Testers — она создана с `hasAccessToAllBuilds`, ручных
действий в ASC больше не нужно. Обработка на стороне Apple — 5–20 минут.
